# nanoc_client

Python client for the **NanoC** computer running inside a Luanti/Minetest
server. Connects to the `nanoc_mod` over TCP (optionally TLS) to act as an
external **terminal** and **source-level debugger**, in parallel to the game.

The wire contract is defined in the sibling repo
[`nanoc_lib`](../nanoc_lib) under `doc/protocol.md`. This client implements
protocol version **2** and validates it during the handshake.

## Install (development)

```bash
pip install -e .
```

## Usage

```bash
nanoc-client --host 127.0.0.1 --port 40000 --token <TOKEN>
# optional TLS: --tls --cafile cert.pem (or --tls-fingerprint <sha256>)
```

The token is generated by the mod per controller and shown to the player
in-game. Commands: `state`, `attach`, `bp <line>`, `step`, `cont`, `vars`,
`bt`, `key <text>`, `help`.

## Terminal TUI (curses)

A live terminal view that renders the termlib screen (colours, cursor moves)
and sends your keyboard/function keys back to the controller:

```bash
nanoc-tui --host 127.0.0.1 --port 41100 --token <TOKEN>
# or: nanoc tui --host ... --port ... --token ...
```

Keys: type + Enter sends a line (leading/trailing spaces are trimmed, like
termlib); **F1–F8** send the termlib function keys;
**Ctrl-C / Ctrl-Q / Ctrl-X** quit. Portability: `curses` is built in on Linux,
macOS and Android/Termux; on Windows install the extra:
`pip install windows-curses` (or `pip install nanoc-client[windows]`).

Reaching a server on another PC: the server admin can enable TLS
(`nanoc_bridge_tls`, see the `nanoc_mod` README) or use an SSH tunnel. With TLS
use `--tls` and one of `--cafile cert.pem` (verified), `--tls-fingerprint
<sha256>` (pinned) or `--tls-insecure` (testing only). Without TLS the traffic
is plaintext and protected only by the token — keep it inside a trusted LAN
and never forward the port on the router.

### TLS certificate (clients)

The certificate is **server-specific and public**. Ask the server owner for
`cert.pem` (or its SHA-256 fingerprint) and store it outside the installed
package, in a per-user directory:

- Windows: `%APPDATA%\nanoc\cert.pem`
  (`C:\Users\<user>\AppData\Roaming\nanoc\cert.pem`)
- Linux: `~/.config/nanoc/cert.pem`
- macOS: `~/Library/Application Support/nanoc/cert.pem`

Use it with `--cafile <path>` (or pin it with `--tls-fingerprint <sha256>`).
For a CA-signed certificate the system trust store is enough; no `cert.pem`
is needed. Do not put the certificate into the extracted ZIP or
`site-packages` (pip updates remove it), and **never copy `key.pem` to a
client**.

Windows examples:

```bat
nanoc read --host <host> --port <port> --tls --cafile "%APPDATA%\nanoc\cert.pem" --token <token>
```

PowerShell: `--cafile "$env:APPDATA\nanoc\cert.pem"`.
VS Code: `"cafile": "C:\\Users\\<user>\\AppData\\Roaming\\nanoc\\cert.pem"`.
MCP: `NANOC_CAFILE=C:\Users\<user>\AppData\Roaming\nanoc\cert.pem`.

Get the SHA-256 fingerprint from the certificate file:

```bash
openssl x509 -in cert.pem -noout -fingerprint -sha256
```

On Windows without OpenSSL, use the Python that runs the client:

```bat
python -c "import ssl,hashlib; der=ssl.PEM_cert_to_DER_cert(open(r'C:\path\to\cert.pem').read()); print(hashlib.sha256(der).hexdigest())"
```

The fingerprint is the SHA-256 of the certificate (not of the file). Pass it
with or without colons: `--tls-fingerprint "AB:CD:..."`, VS Code
`"tlsFingerprint": "..."`, MCP `NANOC_TLS_FINGERPRINT=...`. It changes when the
certificate is renewed. Do **not** use `certutil -hashfile` – that hashes the
file, not the certificate.

## Debugging from VS Code

This repo ships a minimal debugger extension (`vscode/nanoc-debug`) that
starts the `nanoc-dap` adapter and adds syntax highlighting for `.nanoc`
files (`.nc` is accepted as an alias).

Install (build a VSIX, no `vsce` needed), then restart VS Code:

```bash
~/Projekte/nanoc_client/vscode/build-vsix.sh
code --install-extension ~/Projekte/nanoc_client/vscode/nanoc-debug.vsix
```

Open the matching source file locally and add a `launch.json` configuration:

```json
{
  "version": "0.2.0",
  "configurations": [
    {
      "type": "nanoc",
      "request": "attach",
      "name": "NanoC",
      "host": "127.0.0.1",
      "port": 41100,
      "token": "<TOKEN from the controller>",
      "source": "${file}",
      "program": "${file}",
      "upload": true
    }
  ]
}
```

`launch.json` must contain the `version`/`configurations` wrapper; a bare
configuration object is not a valid launch file and VS Code falls back to a
plaintext default (which a TLS bridge rejects with "Connection reset").

If the bridge uses TLS (`nanoc_bridge_tls`), add the TLS settings to the same
configuration. Either trust the server certificate:

```json
  "tls": true,
  "cafile": "C:\\Users\\<user>\\AppData\\Roaming\\nanoc\\cert.pem"
```

or pin its SHA-256 fingerprint (`"tlsFingerprint": "<hex>"`), or disable
verification for testing (`"tlsInsecure": true`). `"serverHostname"` overrides
the name used for certificate verification (default: `host`). Without `tls`
the adapter connects in plaintext and a TLS bridge resets the connection.

After updating the extension, rebuild and reinstall the VSIX (0.4.1) so the new
launch properties and the TUI terminal arguments are available.

With `"upload": true`, F5 uploads the active file (and recompiles) before
attaching. For a **download-only** session omit `upload` (and `program`):
otherwise the controller program is replaced by the active file first, and
"NanoC: Download Program from Controller" returns that file (or 0 bytes if it
is empty).

Start with F5: breakpoints, stepping, call stack and Globals/Locals all work.
Program output (`printf`) is shown in the dedicated **NanoC terminal** — open it
with **NanoC: Open Terminal (nanoc-tui)** (Ctrl+Alt+T) or run `nanoc-tui`
yourself; the Debug Console is reserved for debugger messages. Set
`"terminalInConsole": true` in the launch config to also mirror the program
output into the Debug Console. Program `log("...")` messages always appear in
the Debug Console (channel 4), so you can debug without cluttering the terminal.
While attached, **NanoC: Upload Program to
Controller** (Ctrl+Alt+U) pushes the active editor to the controller
(+recompile), and **NanoC: Download Program from Controller** opens the
controller's program. `.nanoc` files (`.nc` alias) are also linted on save
(via the
local `nanoc-check`); problems appear in the Problems panel and jump to the
line on click (command **NanoC: Check Program (lint)**). Other DAP clients
(nvim-dap, Emacs dap-mode) can use the `nanoc-dap` executable directly.

## Scriptable CLI (`nanoc`)

Non-interactive commands, useful for scripts and AI agents (OpenCode, Claude,
…):

```bash
nanoc check app.nanoc                    # local lint (file:line: error)
nanoc push  app.nanoc --token T          # upload + compile (errors on stderr)
nanoc run   --token T                    # resume the controller
nanoc stop  --token T                    # halt (pause)
nanoc read  --token T --seconds 3        # print terminal output for 3 s
nanoc exec  app.nanoc --token T --seconds 3   # push + run + read (one call)
nanoc scan  --token T --radius 8              # player-centered TA4/TA5 topology as JSON
nanoc catalog --token T                       # Beduino topic catalog as JSON
nanoc tui   --token T                         # open the curses terminal view
```

Connection flags: `--host` (127.0.0.1), `--port` (41100), `--token` (from the
controller form), `--tls`, `--cafile`, `--tls-fingerprint`, `--tls-insecure`.
`nanoc exec` is the one-shot loop for automation: write → exec → read output →
improve.

A newly placed controller with an empty program produces no terminal output.
To check TLS/token/bridge without output, use `nanoc catalog` (returns the
topic catalog) or `nanoc scan --radius 8` (returns the controller/plant if its
area is loaded). `nanoc read` only shows terminal output.

## MCP server (`nanoc-mcp`)

Exposes the bridge to AI clients (Claude Desktop, OpenCode, …) as MCP tools:

`nanoc_scan`, `nanoc_check`, `nanoc_push`, `nanoc_program_get`, `nanoc_run`,
`nanoc_stop`, `nanoc_read`, `nanoc_exec`.

Connection defaults come from the environment (`NANOC_HOST`, `NANOC_PORT`,
`NANOC_TOKEN`, `NANOC_TLS`, `NANOC_CAFILE`, `NANOC_TLS_INSECURE`,
`NANOC_TLS_FINGERPRINT`) or per tool call.

Claude Desktop (`claude_desktop_config.json`):

```json
{
  "mcpServers": {
    "nanoc": {
      "command": "nanoc-mcp",
      "env": { "NANOC_PORT": "41100", "NANOC_TOKEN": "<TOKEN>" }
    }
  }
}
```

OpenCode (`opencode.json`, adjust to your version):

```json
{
  "mcp": {
    "nanoc": {
      "type": "local",
      "command": ["nanoc-mcp"],
      "environment": { "NANOC_PORT": "41100", "NANOC_TOKEN": "<TOKEN>" },
      "enabled": true
    }
  }
}
```

Typical AI loop: `nanoc_scan` → reason about the graph → `nanoc_exec`
(push+run+read) → refine.

### MCP resources (documentation for the AI)

The server also publishes documentation as MCP resources, so a client knows
NanoC and Techage without prior training:

| URI | Content |
|---|---|
| `nanoc://workflow` | How to drive the controller (scan → catalog → check → exec) |
| `nanoc://language` | NanoC code-generation primer |
| `nanoc://reference` | Full language reference |
| `nanoc://manual` | Player manual (language, Techage, timing) |
| `nanoc://topics` | BEP 005 topic table (payloads, node patterns) |
| `nanoc://examples/techage_monitor` | Monitoring example |
| `nanoc://examples/termlib_demo` | Terminal/keyboard example |

The files are vendored in `nanoc_client/docs/`; refresh them from the sibling
repositories with `python tools/sync_docs.py` (see `docs/README.md`).

### OpenCode skill

`skill/nanoc/SKILL.md` bundles the workflow for opencode (when to use the
tools, which resources to read first, the common pitfalls). Install it once:

```bash
mkdir -p ~/.config/opencode/skills
ln -sfn "$PWD/skill/nanoc" ~/.config/opencode/skills/nanoc
```

Restart opencode after changing the MCP config or the skill; both are loaded
at startup only.

## Focus

Only one client may debug a controller at a time. The first `attach` owns it;
other clients stay terminal viewers (they receive output) and get `DENIED` for
control commands. `detach` or disconnect releases the focus.

## Status

- `protocol.py` – framing, handshake, debug command vocabulary (protocol v2)
- `client.py` – blocking TCP/TLS client
- `cli.py` – interactive CLI with a reader thread
- `screen.py` – shared termlib screen emulator (parser + IR, ANSI/Tk renderers)
- `tui.py` – curses terminal TUI (`nanoc-tui`)
- `mock_server.py` – mock server for client testing
- `dap.py` – Debug Adapter Protocol server (`nanoc-dap`) for editors

The Luanti-side bridge is `nanoc_mod/src/bridge.lua`.
